# Spike Report: Report-to-Code — Starter Tailwind Theme / CSS from Frontmatter

**Issue**: #7 (`[DIST-006] Spike: report-to-code — starter Tailwind theme / CSS from frontmatter`)
**Plan**: `.agents/plans/completed/tailwind-theme-spike-plan.md`
**Status**: Spike complete — no `lib/`, `app/`, or `eval/` changes in scope or made. Prototype and spot-check project lived in the session scratchpad, per the DIST-005 precedent.

## Summary

A starter Tailwind v4 `@theme` file is fully derivable from the existing report frontmatter with **zero invented values and zero schema surface** — every emitted line traces 1:1 to a field the report already carries, and every absent lane produces an absent output section (asserted, not eyeballed). The generated file builds cleanly in a fresh Tailwind v4.3.3 project and the expected utilities (`bg-primary`, `text-h1`, `rounded-1`, `p-4`, …) appear in the output CSS with the measured values. Three findings shaped the mapping and are ground-truthed against real builds below: (1) Tailwind v4's `--text-<token>--line-height/--font-weight/--letter-spacing` **sub-key** syntax lets one `text-h1` utility apply all four measured type properties — strictly better than scattering them across `--font-weight-*`/`--leading-*`/`--tracking-*` namespaces; (2) mapping the positional spacing scale to `--spacing-1..n` is a confirmed footgun (it silently shadows Tailwind's numeric `p-1`/`p-2` utilities and produces a non-monotonic scale), while `--spacing: <baseUnitPx>px` makes every measured scale step reachable through stock numeric utilities; (3) `@theme` has no dark variant, but because v4 emits theme variables onto `:root` and utilities reference them via `var()`, a plain `@media (prefers-color-scheme: dark) { :root { … } }` override of the `--color-*` properties — emitted only when `paletteDark` exists — is both honest and functional.

**Recommendation: GO** — ship `emitTailwindTheme(report)` as a new export in `lib/emit.ts` plus a second download button (surface (a)), Tailwind `@theme` flavor only, as a small follow-up story. Detail in §4.

## 1. Findings — frontmatter-field → theme-variable mapping

Every mapping below was exercised against real `Report` objects replayed offline from both eval corpus captures (`clean-light`, `dark-mode`) via `extractFromCapture` — no browser, no network, exactly the eval harness's replay path (`eval/run.ts:52`).

### Mapped (1:1 traceable, build-verified)

| Frontmatter field | Theme variable(s) | Utilities generated (verified in `out.css`) | Notes |
|---|---|---|---|
| `palette.colors[].role/hex` | `--color-<role>: <hex>` | `bg-<role>`, `text-<role>`, `border-<role>`, … | Hyphenated roles (`on-primary`) work unmodified: `text-on-primary` generated |
| `paletteDark.colors[].role/hex` | `@media (prefers-color-scheme: dark) { :root { --color-<role>: <hex> } }` appended **after** the `@theme` block | (overrides the same vars the light utilities reference) | Only when `paletteDark` present — see §1.1 |
| `typography.families[].name/stack/role` | `--font-<role>: <stack>` (first family per role wins; `cssFontName` quoting rule from `lib/emit.ts:286-288`) | `font-body`, `font-mono` | Full measured stack emitted, e.g. `--font-mono: "JetBrains Mono", monospace` |
| `typography.scale[].sizePx` | `--text-<token>: <sizePx>px` | `text-h1` … `text-small` | |
| `typography.scale[].lineHeight/weight/letterSpacing` | `--text-<token>--line-height` / `--text-<token>--font-weight` / `--text-<token>--letter-spacing` (v4 sub-keys) | folded into the same `text-<token>` utility | One class applies all four measured properties — see §1.2 |
| `spacing.baseUnitPx` | `--spacing: <baseUnitPx>px` | all numeric spacing utilities (`p-4` → `calc(var(--spacing) * 4)`) | Chosen over positional `--spacing-1..n` — see §1.3 |
| `radius.scale[i]` | `--radius-<i+1>: <value>` | `rounded-1`, `rounded-2`, `rounded-3` | Positional, mirroring `renderCssVariables`'s existing `--radius-<i>` naming |
| `elevation.shadows[].name/value` | `--shadow-<name>: <value>` | `shadow-sm/md/lg/xl` (override Tailwind's defaults — measured values replace stock ones) | Both corpus reports have `shadows: []`, so nothing was emitted — correct per the empty-`renderElevation` precedent (`lib/emit.ts:234-242`) |
| `source.ref` + `source.capturedAt` | header comment `/* Generated by Distill from <ref> (captured <capturedAt>). */` | n/a | Both are existing frontmatter fields, so the header stays 1:1 |

### Omitted — no honest mapping exists (omitted, never defaulted)

| Field | Why omitted |
|---|---|
| `typography.scale[].sizePxMobile` | Expressing it in a `@theme` file requires a breakpoint to hang the override on, and no breakpoint is a measured frontmatter field — the responsive harvest viewports (390/768) are capture configuration, not page measurements. Fabricating `--breakpoint-*` would violate the measured-never-faked rule. The value stays available in the report body and the plain-CSS flavor's `--font-size-<token>-mobile` (where it's a raw variable, not a claim about when to apply it). |
| `spacing.scale[i]` (positional, in the `@theme` flavor) | Confirmed footgun — §1.3. The plain `:root` flavor keeps `--space-<i>` per the existing `renderCssVariables` naming. |
| `recipes` / `states` | Component-level facts (a Button's padding, a hover delta), not theme tokens. Tailwind's `@theme` defines the design token vocabulary; recipes are compositions *of* those tokens and belong in component code, which a token file must not scaffold. `states` additionally targets palette roles whose hover values are raw measured colors, not theme entries. |
| `identity` / `imageMood` | Interpretive AI lanes — adjectives and image search keywords have no CSS representation at all. |
| `palette.contrast`, `areaWeight`, `provenance`, `wcag` | Report metadata about the measurements, not values a stylesheet consumes. |

### 1.1 Dark palette handling

`@theme` has no dark-variant syntax, so the only honest mapping is a custom-property override. This works *because of* (not despite) v4's compilation model — verified in the spot-check build: the `@theme` variables are emitted as `:root { --color-primary: #1a73e8; … }` and every color utility compiles to `var(--color-…)`, so a later `@media (prefers-color-scheme: dark) { :root { … } }` block re-pointing the same properties flips every utility at once. The override block contains **only** `--color-*` lines (asserted) — `paletteDark` carries no typography/spacing claims, so the override must not either.

A genuine corpus finding en route: **neither corpus report actually carries `paletteDark`.** The `dark-mode` fixture's site is dark *by default*, so its `prefers-color-scheme: dark` render has the same background and `extractDarkPalette` honestly returns nothing (ΔE gate at `lib/extract/palette.ts:490`). The dark-override emission path was therefore exercised with a clearly-labeled synthetic `paletteDark` fixture in the driver (assertions in §2); a real two-scheme site would exercise it end-to-end.

### 1.2 Type scale: sub-keys beat parallel namespaces

The plan left open whether weight/line-height/letter-spacing should map to `--font-weight-<token>` / `--leading-<token>` / `--tracking-<token>`. The spike found Tailwind v4's font-size **sub-key** syntax is strictly better: `--text-h1--line-height`, `--text-h1--font-weight`, `--text-h1--letter-spacing` fold into the single `text-h1` utility. Verified output:

```css
.text-h1 {
  font-size: var(--text-h1);
  line-height: var(--tw-leading, var(--text-h1--line-height));
  letter-spacing: var(--tw-tracking, var(--text-h1--letter-spacing));
  font-weight: var(--tw-font-weight, var(--text-h1--font-weight));
}
```

One class reproduces the full measured type step, and the `--tw-*` indirection means stock `leading-*`/`tracking-*`/`font-*` utilities still override it — exactly the "starter theme" ergonomics wanted. The parallel-namespace alternative would generate `font-h1` / `leading-h1` / `tracking-h1` utilities that the user must remember to co-apply, and `--font-weight-h1` → `font-h1` sits confusingly beside the family utility `font-body` in the same `font-*` prefix.

### 1.3 Spacing: base unit, not positional scale

Both mappings are traceable (both `baseUnitPx` and `scale` are real frontmatter fields), so this was decided empirically. Test: defining `--spacing-1: 8px; --spacing-2: 12px` (positional mapping of the measured scale `[8, 12, 16, 20, 24, 48, 96]`) in a v4 build produces:

```css
.p-1  { padding: var(--spacing-1); }            /* 8px  — shadowed */
.p-1\.5 { padding: calc(var(--spacing) * 1.5); } /* 6px — still multiplier */
.p-2  { padding: var(--spacing-2); }            /* 12px — shadowed */
.p-3  { padding: calc(var(--spacing) * 3); }     /* 12px — still multiplier */
```

Named `--spacing-<n>` entries silently shadow Tailwind's numeric utilities *for exactly the defined names* while every other value keeps multiplier semantics — `p-1` (8px) > `p-1.5` (6px), and `p-2` ≡ `p-3`. A starter file that quietly redefines what `p-1` means is a trap. `--spacing: 4px` (the measured `baseUnitPx`) instead makes the whole numeric namespace speak the site's grid, and — checked against the real corpus values — every measured scale step is a multiple of the base and thus reachable with stock utilities (`8→p-2`, `12→p-3`, …, `96→p-24`). The positional `--space-<i>` naming survives unchanged in the plain `:root` flavor, where nothing consumes the names.

## 2. Prototype

`spike-tailwind-theme.ts` (scratchpad, not committed): `emitTailwindTheme(report)` and `emitThemeCss(report)`, both mirroring `renderCssVariables`'s conditional-lane structure (`lib/emit.ts:296-338`) — palette unconditional (it's the one required lane), every other section behind `if (report.<field>)`. The plain `:root` flavor uses the *identical variable names* as the report body's `## CSS variables` block, so a downloaded file and the in-report block can never disagree; it adds only the header comment, `--spacing-base`, and the dark override block.

Sample `@theme` output (dark-mode corpus, abridged):

```css
/* Generated by Distill from dark-mode.html (captured 2026-07-23T00:37:13.413Z). */
@theme {
  --color-background: #0d1117;
  --color-primary: #58a6ff;
  --color-on-primary: #0d1117;
  --font-body: "IBM Plex Sans", system-ui, sans-serif;
  --font-mono: "JetBrains Mono", monospace;
  --text-h1: 44px;
  --text-h1--line-height: 1.1;
  --text-h1--font-weight: 700;
  --text-h1--letter-spacing: -0.01em;
  /* … h2/h3/body/small … */
  --spacing: 4px;
  --radius-1: 8px;
  --radius-2: 12px;
  --radius-3: 9999px;
}
```

### Omission-behavior assertions (acceptance criterion 2 — asserted, not eyeballed)

The driver replays both corpus captures, then rebuilds each report with every optional lane absent (`{ reportKind, source, palette }` only, the `buildReport` spread-conditional style) and asserts on the emitted strings, for **both** flavors:

- stripped output contains **no** `--font*`, `--text-*`, `--spacing*`, `--space-*`, `--radius*`, `--shadow*`, `--line-height*`, or `prefers-color-scheme` substring — only `--color-*` lines survive;
- dark-override presence exactly equals `Boolean(report.paletteDark)` on the full reports;
- the synthetic-`paletteDark` variant's override block contains the dark hexes and **only** `--color-*` lines.

All assertions passed for both corpus slugs (driver exits 0; a failed assertion exits 1).

## 3. Spot-check — fresh Tailwind v4 project

Fresh project in the scratchpad (`tw-spotcheck/`), nothing shared with the repo install:

```bash
npm init -y && npm install tailwindcss @tailwindcss/cli   # → tailwindcss 4.3.3
# input.css = @import "tailwindcss"; + the generated clean-light @theme file, verbatim
# index.html uses: bg-background text-text font-body text-h1 text-primary text-body
#   text-muted bg-primary text-on-primary rounded-1 rounded-3 p-2 p-4 bg-surface text-small border-border
npx @tailwindcss/cli -i input.css -o out.css               # → "Done in 81ms", exit 0
```

Verified in `out.css`:

- every class used in `index.html` was generated, with the measured values (`--color-primary: #1a73e8` on `:root`, `.bg-primary { background-color: var(--color-primary) }`);
- `.text-h1` carries all four sub-key properties (§1.2 listing is pasted from this build);
- `.p-4` → `calc(var(--spacing) * 4)` = 16px against the measured 4px base;
- second build with the synthetic-dark theme file: exit 0, the `@media (prefers-color-scheme: dark)` block appears in `out.css` *after* the `:root` theme variables, so the cascade resolves the override correctly;
- the positional-spacing footgun build (§1.3) — also exit 0, which is precisely the problem: it builds fine and silently means the wrong thing.

## 4. Recommendation

**GO**, as a small follow-up story. Delivery surface:

- **Ship (a): a new exported `emitTailwindTheme(report: Report): string` in `lib/emit.ts` + a second download button** in `app/page.tsx` next to the existing `downloadActiveMarkdown` (`app/page.tsx:133-148`), enabled on the design-report tabs. The emitter is a pure `Report → string` function exactly like `renderMarkdown` — no new dependency, no API surface, trivially unit-exercisable, and available to API consumers who already receive the report object.
- **Not (b)** (a fourth tab, `app/page.tsx:55`): a theme file is a *download artifact*, not a browsing surface — a tab showing a wall of CSS variables duplicates the existing `## CSS variables` block in the preview tab.
- **Not (c)** (appending another fenced block to the markdown body): the body already ends with the `:root` CSS-variables block; appending a near-duplicate `@theme` fence bloats every report for a file whose whole value is being *saved as a file*. It would also put two subtly different spacing representations (`--space-<i>` vs `--spacing`) in one document.
- **Flavor: Tailwind `@theme` only.** The plain `:root` flavor already ships today as the report body's `## CSS variables` block — copy-pasteable as-is. Shipping a second, slightly-different `:root` file (header + `--spacing-base` + dark block) adds a confusable artifact for marginal value; if demand appears, the dark-override block can be added to `renderCssVariables` instead (it satisfies the same 1:1 rule).
- **Derived view, no schema change — confirmed explicitly**: the prototype consumes only existing `Report` fields, adds zero fields to `reportSchema`, and follows the same conditional-lane guards as `renderCssVariables`. Nothing in this spike motivates schema surface.

### Follow-up story sketch

| Story | Scope | Complexity |
|---|---|---|
| Tailwind theme download | `emitTailwindTheme` in `lib/emit.ts` (mapping per §1, including the §1.2 sub-keys, §1.3 `--spacing` choice, §1.1 dark block); download button in `app/page.tsx`; exercised via the eval-corpus replay pattern | Small (the mapping is fully specified and build-verified by this spike) |

Open item for the story (not a blocker): the button needs the theme generated client-side from the already-returned `report` object (the emitter is isomorphic — string building only), or returned alongside `markdown` from the API route; the former adds zero payload and is the natural fit.
